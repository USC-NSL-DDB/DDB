# ADR 0001: Protobuf is the canonical v2 contract

Status: accepted

Date: 2026-08-14

## Context

DDB's v1 HTTP JSON was designed around a small set of existing handlers. Making
that representation the semantic source would bind future frontends to Axum,
Serde defaults, and backend-shaped values. DDB needs one versioned definition
that supports efficient native clients, a browser-friendly JSON binding,
generated SDKs, compatibility checks, and replayable event streams.

## Decision

The canonical public package is `ddb.api.v2`, written consistently in
`proto3` syntax supported by the repository's Prost toolchain.

Protobuf declarations define stable requests, responses, resources, errors,
events, capabilities, and extension envelopes. Binary Protobuf and standard
ProtoJSON are peer encodings of those declarations. HTTP/OpenAPI, event
AsyncAPI, gRPC, Connect, stdin, and future DAP adapters are bindings; none is a
second semantic API.

V1 remains a separate compatibility surface. V2 is additive and runs beside v1
until the published migration policy permits v1 retirement.

The schema is generated by one repository tool with mutating `generate` and
non-mutating `--check` modes. Buf STANDARD lint, FILE breaking checks,
descriptor reproduction, and binary/ProtoJSON goldens gate changes.

## Consequences

Frontend authors can generate types for their language and choose transport
without learning GDB/LLDB MI payloads. DDB core must implement a
transport-independent application service and adapters must convert at its
boundary.

ProtoJSON costs more CPU and bytes than binary Protobuf, but it remains required
for browser and debugging accessibility. Native transports can use binary
Protobuf without changing semantics.

Names and field numbers become long-lived public commitments. Review must reject
transport convenience fields that do not represent stable debugger semantics.
