# DDB API v2

DDB API v2 is the public, backend-neutral contract for TUI, IDE, web, and other
community debugger frontends. Protobuf defines the canonical types. Native
Protobuf and HTTP/ProtoJSON bindings share one application-service
implementation; transport adapters do not call private runtime managers.

Current status: the canonical schema, generated Rust/TypeScript/Python types,
descriptor, transport-independent application service, HTTP/ProtoJSON binding,
public SDKs, black-box conformance runner, and an opt-in Tonic gRPC preview are
implemented. The existing v1 and stdin interfaces remain live compatibility
surfaces. API v2 and its packages remain preview-stage.

## Contract layout

- `common.proto`: request metadata, routing targets, pagination, typed errors,
  cursors, preconditions, and bounded dynamic values.
- `resources.proto`: debugger resources, capabilities, limits, snapshots, and
  asynchronous operations.
- `debugger_service.proto`: read, control, and admin methods.
- `event_service.proto`: replayable state events and the independent output
  lane.
- `extension.proto`: namespaced descriptors, presentation hints, actions, and
  bounded extension payloads.

Generated Rust DTOs are published by `ddb-api-types`. They contain wire types
only and do not depend on DDB core. `V2_FILE_DESCRIPTOR_SET` is available for
reflection, compatibility tooling, and language SDK generation.

Generated transport descriptions are checked in at:

- `generated/openapi-v2.json` for all HTTP/ProtoJSON RPCs;
- `generated/asyncapi-v2.json` for state and output NDJSON streams.

Both documents are generated from the same descriptor as the Rust DTOs and
validated in CI. TypeScript interfaces and Python `TypedDict` contracts and
method registries are generated from that descriptor in the same drift check.
Do not edit generated artifacts directly.

## Frontend SDKs and conformance

- Rust: `ddb-api-client` (HTTP baseline), `ddb-api-types`, and the opt-in
  `ddb-api-grpc` transport stubs.
- TypeScript: [`sdk/typescript`](../../sdk/typescript/README.md), with no runtime
  dependency and support for Node.js 18+ and modern browser Fetch/Web Streams.
- Python: [`sdk/python`](../../sdk/python/README.md), a typed Python 3.11+
  client with no runtime dependency outside the standard library.

All frontend SDKs own URL construction, bearer authentication, request
deadlines, mutation idempotency keys, typed errors, bounded pagination,
operation polling, NDJSON parsing, replay-aware reconnect, and shutdown. Their
source imports only public contracts. Maintained inspection, event, breakpoint,
and distributed-backtrace examples live under each SDK's `examples/` directory.

Operators and alternative server implementations can run the public-SDK-only
`ddb-api-conformance` binary. Its default read-only profile does not mutate the
debugger. The `mock` profile requires a disposable Mock DDB and CONTROL token:

    cargo run -p ddb-api-conformance -- \
      --endpoint http://127.0.0.1:5000 \
      --profile mock --output json

The report is credential-free structured evidence; any failed check exits with
status 2.

## HTTP binding

Every RPC is an HTTP `POST` under:

    /api/v2/rpc/<fully-qualified-service>/<method>

Unary requests and responses use canonical ProtoJSON with
`Content-Type: application/json`. Streaming responses use
`application/x-ndjson`: each non-empty line is one canonical ProtoJSON event,
and an empty line is a transport heartbeat. State and output subscriptions are
separate requests and have independent backpressure behavior.

Protected methods accept `Authorization: Bearer <token>`. Effective
authentication mode and limits come from `GetCapabilities`; never infer them
from the example development configuration. See `examples/` for curl and
dependency-free TypeScript clients.

Operators can tune API-owned replay, subscriber, output-record, and operation
retention through `Conf.ApiLimits`; the runtime uses the same effective values
it advertises. The public limits include count, age, total-byte, per-record,
per-subscriber, encoded-response, source-file, source-window, memory-read, and
variable-expansion bounds. Unary responses are checked after ProtoJSON
encoding; source eligibility and source windows have separate advertised
limits. See [`operations.md`](operations.md) for the exact configuration and
startup ceilings.

## Native gRPC preview

The native binding remains deliberately non-default. Three retained
release-build comparisons found about a 15% p95 improvement for full snapshots,
below the roadmap's 20% promotion threshold, and did not cover the broader
resource-cost and mixed-workload matrix. [ADR 0005](adr/0005-transport-policy.md)
records the evidence and decision. Build it explicitly:

    cargo build -p ddb --features grpc-preview

Then assign a distinct, non-zero loopback port in the DDB configuration:

    Conf:
      api_server_port: 5000
      api_grpc_preview_port: 50051
      api_auth_token_file: "/secure/path/ddb-api-tokens.json"

The process refuses this configuration when the binary was built without
`grpc-preview`, and rejects port zero or a collision with
`api_server_port`. The preview listener always binds to `127.0.0.1`; it does
not create a remote-exposure shortcut. The same token file and READ, CONTROL,
and ADMIN scope hierarchy protect HTTP and gRPC. Standard gRPC health and
reflection also require READ permission.

Clients should use the generated stubs in `ddb-api-grpc` and the messages in
`ddb-api-types`. Every ordinary method is unary. State and output are
independent server streams. Discovery advertises the exact enabled gRPC URI and
`WIRE_ENCODING_PROTOBUF`; a missing gRPC endpoint means clients must use the
mandatory HTTP binding.

The listener enforces 4 MiB decoded-request and 16 MiB encoded-message limits,
bounded per-connection request/stream concurrency, bounded header size,
HTTP/2/TCP keepalive, and graceful shutdown. Tonic enforces standard
`grpc-timeout` deadlines, while the Protobuf `RequestContext.deadline`
retains identical cross-transport semantics. Application failures use the
normal gRPC status code and place the binary `DdbError` message directly in
status details; clients must use its stable error code and fields instead of
parsing status text.

Compression is intentionally not enabled globally in the preview. It will be
added only with measured payload thresholds so small interactive controls do
not pay unconditional compression cost.

## Required frontend workflow

A frontend should implement this sequence:

1. Call `GetServerInfo` and `GetCapabilities`. Render controls from
   capabilities instead of hard-coding a backend feature matrix.
2. Call `GetSnapshot` with the required bounded sections. Store its
   `server_instance_id`, `state_event_cursor`, and
   `base_state_revision`.
3. Subscribe to state events after that cursor. Apply only newer resource
   revisions; duplicate upserts and tombstones are harmless.
4. If subscription returns `REPLAY_GAP`, or a required-resync event appears,
   discard the local projection and repeat snapshot hydration.
5. Subscribe to output separately. Output gaps are presentation loss and do not
   imply state-event loss.
6. Submit every mutation with a fresh idempotency key. Retain the returned
   operation ID and observe operation events or poll `GetOperation`.
7. Treat command admission, target running state, and later stopped state as
   distinct facts.
8. Re-read capabilities when a capability-change event arrives.

Clients must use opaque IDs as strings and must not calculate with them. Source
lines and columns are one-based. Target addresses are strings because width and
syntax are target dependent.

## Operations and errors

Every admitted control request returns an `Operation`, including fanout,
extension, and admin mutations. Retrying the same mutation with the same
idempotency key during its retention window returns the original operation.
Operation records are bounded and expire; they are not an audit log.

All transports map the same `DdbError`. HTTP and gRPC status codes are
transport mappings, not separate semantics. Partial fanout failure is explicit
through per-target outcomes. Cancellation is offered only when both capabilities
and the current operation record say it is supported.

The raw command method is a compatibility escape hatch. Its command language
and decoded payload semantics are not part of the stable typed API. Clients
should prefer typed operations whenever capabilities advertise them.

## Breakpoint lifecycle

Use `CreateBreakpoint`, `UpdateBreakpoint`, and `DeleteBreakpoint` rather than
raw MI commands. Breakpoint and sub-breakpoint IDs are opaque; a distributed
breakpoint remains one logical resource even when DDB installs a backend-local
copy in every session of a group.

Creation applies `enabled`, `condition`, `temporary`, and `hardware` as part of
the debugger's insertion command. In particular, `enabled: false` never creates
an observable enabled breakpoint and then disables it in a second command.

`UpdateBreakpoint.update_mask` currently accepts `enabled`, `condition`, or
both. In HTTP/ProtoJSON, `google.protobuf.FieldMask` uses its canonical
comma-separated string form, for example:

```json
{
  "breakpointId": "bpt_...",
  "breakpoint": {
    "enabled": false,
    "condition": "request.id == 42"
  },
  "updateMask": "enabled,condition"
}
```

To clear a condition, include `condition` in `updateMask` and omit
`breakpoint.condition`. Duplicate, empty, or unsupported mask paths fail
explicitly. `enabled` has explicit scalar presence: create omission defaults to
`true`, an update whose mask includes `enabled` must send it, and resource
responses always populate it. This preserves explicit `false` in ProtoJSON.

DDB applies a combined update to every debugger-local copy before committing
the logical breakpoint and publishing its new revision. If any target rejects
the update, DDB leaves the logical resource unchanged and rolls back copies
already changed. A debugger disappearing during rollback is reported and
logged as backend failure; no distributed transaction with an external
debugger process is implied.

Group-scoped create and delete operations can finish in
`OPERATION_STATE_FAILED` with `DDB_ERROR_CODE_PARTIAL_FAILURE` when only some
debuggers accept the request. The operation includes a per-target outcome for
every attempted session and a typed breakpoint result representing the local
copies that still exist. Frontends must retain and render that result so the
user can retry or delete the remaining copies. A create for which every target
fails does not create a logical resource; a fully successful delete removes it.

Conditions, temporary breakpoints, and enable/disable are available on both
GDB and LLDB. Hardware breakpoints are advertised and accepted only when the
configured backend supports them; the LLDB bridge returns typed `UNSUPPORTED`
with required capability `breakpoints.hardware` instead of silently creating a
software breakpoint. Frontends must render these controls from
`GetCapabilities`.

## Event model

State and output are separate logical lanes:

- State events are ordered, revisioned, retained within advertised bounds, and
  replayable. They are published only after the corresponding domain mutation
  commits.
- Output is high-volume and independently backpressured. Replay is optional and
  loss is represented by an explicit `OutputGap`.

A snapshot cursor is captured before detached state collection. A client may
therefore observe a resource in the snapshot and replay the event that produced
it; resource revisions make that duplicate safe.

## Schema workflow

Prerequisites are Rust, Cargo, `protoc` with the standard well-known-type
include files, and Buf 1.x. CI pins the Buf CLI version.

After editing `proto/ddb/api/v2`:

    buf format -w
    buf lint
    cargo run -p ddb-api-codegen -- generate
    cargo run -p ddb-api-codegen -- --check
    cargo test -p ddb-api-types --all-targets
    npm ci --prefix sdk/typescript --ignore-scripts
    npm test --prefix sdk/typescript
    PYTHONPATH=sdk/python/src python3 -m unittest discover -s sdk/python/tests

The generator writes through a temporary directory, omits descriptor source
information, and changes checked-in artifacts only when their bytes differ.
The check mode never rewrites files. It also verifies local schema references
and proves that every Protobuf RPC is represented in OpenAPI, while every and
only server-streaming RPC is represented in AsyncAPI.

See `compatibility.md` before changing any released declaration. Architecture
decisions under `adr/` explain the contract and extension boundaries.

Frontend migrations should follow
[`migration-v1-to-v2.md`](migration-v1-to-v2.md). Contributors adding a field,
method, event, capability, extension, transport mapping, or conformance vector

SDK/server version ranges and the non-publishing package gate are documented in
[`sdk-compatibility.md`](sdk-compatibility.md). Public API and SDK changes must
